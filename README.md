# Polza Agency — тестовое задание

Тут лежит загрузка ~1000 компаний из JSON-страниц и `review.csv` в PostgreSQL,
плюс страница `/companies` на Next.js поверх этой базы.

Стек как в задании: Next.js 15 (App Router), TypeScript, PostgreSQL 16.
Всё поднимается в Docker, ставить руками ничего не надо.

Куда смотреть:

- [`schema.sql`](schema.sql) — схема базы, с комментариями почему так
- [`queries.sql`](queries.sql) — три запроса из задания
- [`ANOMALIES.md`](ANOMALIES.md) — что не так с `review.csv`, там самое интересное
- [`ANSWERS_TASK4.md`](ANSWERS_TASK4.md) — ответы на четвёртую задачу
- [`screenshots/`](/screenshots) — скриншоты страницы

## Как запустить

Нужен только Docker. Я проверял на Docker 29 и Compose v5.

```bash
cp .env.example .env
docker compose run --rm loader
docker compose up -d web
```

Первая команда копирует конфиг — значения по умолчанию рабочие, трогать их
не обязательно. Вторая поднимает Postgres, создаёт схему, грузит обе выгрузки
и пересобирает `ANOMALIES.md`. Вместе со сборкой образа это примерно минута.
Третья запускает страницу — открывай http://localhost:3000/companies

Убедиться, что данные доехали:

```bash
docker compose exec db psql -U polza -d polza -c "SELECT count(*) FROM companies;"
# 1178
```

Если надо снести всё вместе с данными — `docker compose down -v`.

## Команды

Если хочется по шагам, а не всё сразу:

| Команда | Что делает |
| --- | --- |
| `docker compose run --rm loader` | всё сразу: схема → JSON → CSV → отчёт |
| `docker compose up -d web` | страница на порту 3000 |
| `npm run db:schema` | накатить схему, можно сколько угодно раз |
| `npm run load:json` | залить `page_*.json` |
| `npm run load:csv` | залить `review.csv` |
| `npm run report` | пересобрать `ANOMALIES.md` из базы |
| `npm run queries` | выполнить `queries.sql` и показать результаты |
| `npm test` | 24 проверки логики нормализации |

Скрипты работают и без контейнера загрузчика — нужен Node 22 и `DATABASE_URL`
на `localhost:5433` (в `.env.example` эта строчка есть, просто закомментирована).

```bash
npm install
npm run load:all
npm run dev
```

## Почему база устроена именно так

**Города и категории вынес в справочники.** В `review.csv` один и тот же город
приезжает как «Москва», «москва», «Москва » с пробелом, «Moscow» и ещё
`РњРѕСЃРєРІР°` в битой кодировке. Если хранить город строкой прямо в таблице
компаний, то любой `GROUP BY city` разъезжается на пять «Москв» и отчёт по
городам врёт. Справочник плюс канонизация на входе закрывают это в одном месте.

**У рейтинга разрешён NULL.** «Рейтинга нет» и «рейтинг ноль» — это разные
вещи. Таких записей 79, и если подставить им нули, средние поедут вниз.

**Дедупликация в три уровня:**

1. по `id` — он стабилен между выгрузками, так что первичный ключ и UPSERT;
2. по ключу «название без кавычек и орг-формы + город + адрес»;
3. по телефону и сайту — тут не отбраковываю, просто помечаю в логе.

Второй уровень появился не от любви к абстракциям. Шесть компаний в
`review.csv` приехали второй раз под id `c_9000xx` и отличаются от уже
загруженных только кавычками в названии: «АО «Флагман Лаб»» против
«АО Флагман Лаб». Сравнение строк в лоб такую пару не поймает. Подробнее — в
[ANOMALIES.md](ANOMALIES.md).

**Индексы** под конкретные запросы: btree на `city_id` и `category_id` для
фильтров, GIN с `pg_trgm` на названии для поиска подстроки (обычный btree на
`ILIKE '%…%'` просто не работает), и частичный индекс на `(city_id, rating)`
при `reviews_count >= 10` — ровно под второй запрос из задания.

**Ничего не выбрасывается молча.** Всё, что не прошло валидацию, лежит в
`staging_rejects` целиком, с причиной. Всё, что я поправил на лету, — в
`load_fixes`, со старым и новым значением. Из-за этого `ANOMALIES.md`
собирается запросами к базе, а не пересказом логов: любую находку можно
перепроверить самому, а не верить мне на слово.

**Повторный запуск ничего не ломает.** Прогонял три раза подряд — 1178
компаний, 29 строк в карантине, 13 правок, цифры не шевелятся. Сначала
шевелились: журналы накапливались между прогонами, и после второго запуска
отчёт показывал 196 дублей вместо шести. Починил, теперь каждый прогон
затирает свои предыдущие записи.

## Страница /companies

Лежит в [`src/app/companies/page.tsx`](src/app/companies/page.tsx), это Server
Component. Запрос к Postgres уходит на сервере, в браузер приходит уже готовая
разметка, строка подключения на клиент не попадает. Внутри таблица, поиск по
названию, фильтры по городу и категории, пагинация по 25 записей.

Фильтры — обычная форма с `method="get"`, состояние живёт в URL. Поэтому
работает кнопка «назад», ссылку с фильтром можно кинуть коллеге, и всё это без
единой строчки клиентского JS.

Ещё есть [`GET /api/companies`](src/app/api/companies/route.ts) — та же выборка,
только JSON. Странице он не нужен, я добавил его чтобы дёргать curl'ом и быстро
видеть цифры.

Секретов в репозитории нет, только `.env.example`. Настоящий `.env` в
`.gitignore`.

### Как проверял

Начал со скучного: снёс всё через `docker compose down -v` и поднял заново
одной командой из README. Хотелось убедиться, что инструкция не врёт и любой
человек получит тот же результат.

Дальше тыкал страницу в браузере и параллельно дёргал `/api/companies` через
curl — так быстрее видно цифры, чем глазами по таблице. Проверил, что поиск
регистронезависимый: «Сфера» и «сфера» дают одинаковые 30 результатов. Что
поиск и фильтр по городу работают вместе, а не отменяют друг друга — 30
сужается до 6 по Москве. Что после отправки формы фильтры остаются выбранными.
Что страницы пагинации не пересекаются — сравнил id с первой и второй,
пересечение нулевое.

Потом ломал специально. Вбил `'; DROP TABLE companies;--` в поиск — вернулось
0 результатов, таблица на месте, запросы параметризованные. Вбил `%` и `_` —
тоже 0, потому что LIKE-шаблоны экранируются; без этого `%` вывалил бы всю
базу. Вбил `<script>alert(1)</script>` — в HTML пришло экранированным.
Скормил `page=0`, `page=99999`, `page=abc`, `per_page=-5`, `per_page=9999` —
всё зажимается в границы, пятисотых не поймал. Отдельно посмотрел, что в HTML
не утёк ни пароль, ни строка подключения.

Ломалось по ходу три раза. Первое: пул подключений создавался при импорте
модуля, то есть раньше, чем скрипт успевал прочитать `.env` — падало с
«DATABASE_URL не задан» при совершенно нормальном файле. Сделал инициализацию
ленивой.

Второе и самое противное: починка битой кодировки молча не работала. Таблицу
CP1251 я набирал руками и опечатался — вышло 127 символов вместо 128, из-за
чего все байты выше `0x80` съехали на единицу. Симптом был странный: города
чинились нормально, а названия с кавычками нет. Полез сравнивать байты
посимвольно, увидел, что «ћ» вообще не находится в таблице. Выкинул свою
таблицу и взял `iconv-lite`, который и так уже был в зависимостях.

Третье: повторный запуск раздувал отчёт. Карантин накапливался между
прогонами, и `ALREADY_IN_DB` показывал 196 вместо 6 — потому что во второй раз
загрузчик сравнивал строки файла с их же копиями, которые сам и вставил.
Заметил только потому, что прогнал загрузку дважды подряд.

На логику нормализации написал 24 проверки (`npm test`) — там, где ошибка тихая
и глазами её не увидишь. Самая полезная из них следит, чтобы чистые русские
названия вроде «Ростов-на-Дону» не менялись после починки кодировки. Иначе
лечение выходит хуже болезни.

## Что осталось за рамками

**Быстрая загрузка.** Скрипты синхронные, вставка построчная. На 1200 записях
это доли секунды, на сотнях тысяч понадобится `COPY` и батчи.

**Авторизация на странице.** Задание её не просит, так что `/companies` открыт
всем, кто дотянется до порта. Для внутренней платформы это надо закрывать.

**Валидация email.** В критериях оценки упомянуты «реальные, валидные email»,
но поля с email в выгрузке нет вообще — ни в JSON, ни в CSV. Я проверил оба
формата. Добавлять пустую колонку не стал; похоже, поле просто не попало в
архив.
